The README now recommends Deno. The evidence supports that ranking, but one observation is unexplained and should be understood before the claim hardens.

Observed with the pinned yt-dlp on macOS arm64, node 24.19.0 and bun 1.3.13 both on PATH:

  [debug] JS runtimes: deno-2.9.5
  [debug] [youtube] [jsc] JS Challenge Providers: bun (unavailable), deno, node (unavailable), quickjs (unavailable)

Yet probing yt_dlp.utils._jsruntime directly reports all three supported:

  DenoJsRuntime -> JsRuntimeInfo(name='deno', version='2.9.5', supported=True)
  NodeJsRuntime -> JsRuntimeInfo(name='node', version='24.19.0', supported=True)
  BunJsRuntime  -> JsRuntimeInfo(name='bun',  version='1.3.13', supported=True)

Versions clear the gates (node MIN 22.0.0; bun MIN 1.2.11, MAX 1.3.14), so detection is not the blocker. Leading hypothesis: the vendored solver directory ships yt.solver.core.js, yt.solver.deno.lib.js, and yt.solver.bun.lib.js but no node lib, so providers without a bundled script variant need a remote fetch (--remote-components ejs:github|npm) and stay inactive by default. That does not explain bun, which does have a vendored lib.

Why it matters: if node and bun cannot activate without a network fetch, then Deno is not merely preferred, it is the only runtime that works offline out of the box, and the README should say so plainly.

Verified for reference: yt-dlp preference values are deno 1000, node 900, quickjs 850, bun 800; only the Deno provider passes sandbox flags (--no-remote, --no-npm, --no-config, --no-lock, --node-modules-dir=none, --no-code-cache, --no-prompt); bun.py carries a deprecation notice pointing at yt-dlp/yt-dlp#16766.
