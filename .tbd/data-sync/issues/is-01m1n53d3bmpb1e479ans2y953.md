AUDIT of the transcription path for long media (no run needed to see this):

There is no chunking or stitching — good for timestamp integrity, since the whole downsampled 16k mp3 is sent as ONE Deepgram request (transcription_deepgram.py reads the file into memory and calls listen.v1.media.transcribe_file). So there are no chunk-boundary artifacts to validate.

The problem is the fixed timeout: RequestOptions(timeout_in_seconds=500). For this 5.3-hour podcast the 16k mono mp3 is roughly 70-80 MB; upload plus Deepgram batch processing (very roughly 20-40x realtime for 18,951 seconds of audio) plausibly lands near or beyond 500s, so the request may abort after minutes of work with a timeout rather than a useful error.

Options, in order of preference: scale the timeout with audio duration rather than fixing it at 500s; or use Deepgram's asynchronous callback flow for long files, which is what they recommend above short clips; or chunk with overlap and stitch, which is the worst option here because it reintroduces boundary artifacts in exactly the timestamps everything downstream depends on.

Also minor: log.save_object writes the entire Deepgram response for a 5-hour transcript.

VALIDATE: watch whether this run's transcribe step completes, and how long the request actually takes.
